# M5：Core 本轮综合验收（2026-10-25）

**结论：本轮Core组合验收通过。** 范围是固定成员、Core生成的合法RPC、小规模日志（新增组合场景最多130条）的确定性场景；不是所有输入/故障穷举，不代表真实Raft集群或KV apply已经实现。下一阶段M6尚未开始。

先读[节点与角色调用图](raft-core-flow.md)，再读`tests/test_raft_core_scenarios.cpp`。测试的`Cluster`只是调度器：一份`Message`表示一份待投递消息，选中才交给目标节点。没有TCP、后台Raft线程或真实选举时钟。

## 2. 统一调度器的12组场景

每个节点独立拥有真实StateStore/LogStore。重启是在同一测试进程内销毁旧Core/日志对象（不是kill -9子进程），重开文件并用恢复值初始化新Core，而不复制旧内存。

| 组 | 谁遇到什么 | 实际检查 |
|---|---|---|
| 1 | 三节点选举、连续提案；同一数据请求重复抵达 | 保存→复制→ACK→leader提交→通知follower；二进制命令；重复请求不增加索引/重复提交 |
| 2 | 节点3掉队130条后恢复 | 真实文件接收64+64+2；每条回复使用自己的原请求；最终match130/next131 |
| 3 | 三节点同时自投；五节点重复一张赞成票 | 分票后更高任期选举恢复；重复票不能凑出多数 |
| 4 | 五节点切成旧leader所在2个与另外3个 | 2/5不能提交；3/5选新leader并提交；恢复后只替换旧的未提交后缀 |
| 5 | 旧成功回复晚于新成功且重复抵达 | 原sent不被新请求覆盖；match/提交不退、不重报 |
| 6 | 真实旧拒绝晚于新重试成功 | 按前一条回退追平；迟到NACK不能撤销已确认进度 |
| 7 | 旧RPC回复带较高term，新RPC仍在途 | 不直接丢弃旧回复；先保存高term、退位并清除本机在途状态 |
| 8 | 同任期Candidate收到有效leader心跳 | 退为Follower、消费重置计时器标志、保留同任期已投的票 |
| 9 | 投票已保存但授票回复丢失，随后重启 | 新Core恢复term/vote，拒绝同任期另一候选人 |
| 10 | 日志尾部追加不完整的2字节后重启 | 真实LogStore修尾→新Core→新选举；当前任期条目使旧前缀重新得知提交 |
| 11 | 完整记录魔数损坏后重启 | 拒绝启动Core，不当作残尾截断，不发布消息或领导状态 |
| 12 | 单节点竞选保存失败；Follower新term保存失败 | 私有状态目录移走造成真实路径失败；不发布领导行为/成功ACK或提交 |

调度器在这些轨迹中持续检查：磁盘term/vote与可用Core相符、term不倒退、同节点同term不换票、同term不出现两个已发布leader、leader包含已知提交内容、单次启动内新增提交区间连续不重报、各节点曾确认的持久化前缀不被替换、同一领导任期match不退且其他peer的next不越过边界。

## 3. 哪些是测试外层的责任

- 一轮Core事件后先完成必要保存，再把依赖它的消息加入队列；失败停止，不猜回滚。
- 每peer只允许一个未过期复制请求。超时可发新请求，但旧消息仍可能抵达；回复保留不可变原sent。`Message.rpc`只属于测试，没有给生产报文悄悄新增RPC ID。
- 外层显式触发选举超时、心跳和请求超时；重置标志只做事件计数，没有选择真实毫秒参数或证明时钟调度。
- 选举不会自动提交旧term日志；需要外层提供当前任期条目。本轮用正常提案作为锚点，没有新增自动no-op逻辑。
- commitIndex在重建Core后从0开始。测试允许跨重启重新通知旧提交前缀，仅核对内容相同；**不证明重复执行KV安全，也未实现lastApplied恢复。**

检查器的全局已提交记录只用于断言，绝不拿它替Core补日志、投票或决定提交。

- 严格编译：实际Core、新场景文件使用C++17 / `-Wall -Wextra -Werror`；脚本`bash -n`通过。
- 完整普通回归：36/36通过，最新日志`build/test-logs/m5-final-run-all.log`；本轮较早的一轮完整36项也通过。
- 新场景12组及R4/follower10组：普通和ASan/UBSan均通过。日志`m5-scenarios-normal.log`、`m5-scenarios-asan.log`、`m5-boundary-green.log`、`m5-follower-asan.log`。
- 配置的ASan/UBSan runner复测通过，背压与单节点E2E确实执行：`build/test-logs/m5-asan-recheck.log`。
- **中途有一次ASan runner整体失败，不能删掉。** `m5-final-run-asan.log`中各单元目标均退出0，但背压服务器启动探测未通过；保存的服务器日志后来出现`bind failed : Address already in use`。当时探测失败日志尚只有`sync mode = always`，不能完整重建时序或断言占用者。
- 后查9006无监听/残留kvserver；默认库约616MiB（645,945,199字节）。实际拥有进程的启动探针测得2.864秒并核对监听PID，未复现5秒探测超时，因此**没有确诊默认库大小就是原失败根因**。未删默认库、未改阈值或网络脚手架，按原配置复测通过。
- 不是36组全部运行sanitizer；自定义分配失败等仍普通覆盖。LeakSanitizer关闭，本轮未跑TSan，也未运行`--slow`附加门禁。
